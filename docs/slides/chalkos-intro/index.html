Nix builds the images and nothing else; chalkctl delivers images and YAML and never runs Nix, so the machine that operates the nodes needs no Nix. A NixOS machine changes in place with nixos-rebuild; a chalkos node has no Nix daemon and no switch-to-configuration, so only config changes without a reboot.

1 EFI boot of a signed UKI

systemd-boot starts one UKI per slot. Kernel, initrd and command line sit under one signature.

2 A/B slots, root hash as identity

An upgrade writes the inactive slot. The store's dm-verity root hash names the image; there is no version number.

3 Encrypted STATE and VAR

LUKS2 with keys sealed by the TPM. STATE holds config and certificates, VAR what services write; root is a tmpfs.

05 / 16
The db key never enters /nix/store; chalkbuild signs a copy on the machine that holds it. dm-verity checks 4 KiB blocks on read. Fallback keyslot is the recovery key by default, or a password, or none; the recovery key derives from the secrets file and the node name. Clients: the secrets file issues a one-hour admin certificate that is never written to disk; chalkctl client new --role issues client files; the node role may only renew. Control planes hold a node CA that issues node certificates only. An operator upgrade carries no config. In maintenance mode chalkctl pins the node's self-signed certificate by its SHA-256 fingerprint; the console uses a root-only socket and each method says whether the console may call it.

Disks tied to the machine

STATE, VAR and volumes are LUKS2, keys sealed by the TPM to the Secure Boot state.

  • Same db key: upgrades unlock unattended
  • Disk moved or Secure Boot changed: no unseal
  • Fallback: the node's recovery key
chalkd is the only way in

Node API on TCP 50000, mutual TLS, client chain checked on every request.

reader<operator<admin
  • No SSH, no login
  • Client files of one role each
Ending access

No revocation list on nodes: access ends with the certificate, or a rotation.

  • chalkctl rotate os-ca cuts old certificates off
  • chalkctl node revoke on Kubernetes
  • The OS CA key stays in the secrets file

The flake follows the homelab example; the extensions line and the bgp.enable toggle are added for illustration. A platform adds the console, agents and drivers of a kind of machine, and mkImages also builds the installer. Rules that read facts run on the node only; chalkctl runs the others. The router layer's validator also runs in chalkctl. Turning a feature off also removes its effects and diagnostics, and the image then rejects its kinds.

Customise with plain NixOS modules

mkImages · layers · extensions · toggles
flake.nixafter the homelab example
images = chalkos.lib.mkImages {
  revision = self.rev or self.dirtyRev or null;
  images = [
    {
      name = "router-metal";
      platform = "metal";
      modules = [ chalkos.nixosModules.router ];
    }
    {
      name = "node-metal";
      platform = "metal";
      modules = [
        chalkos.nixosModules.kubernetes
        ./extensions      # your kinds
        { chalkos.kubernetes.bgp.enable = false; }
      ];
    }
  ];
};

One layer per image, plus a platform: metal or kvm.

07 / 16
A kind has fields as NixOS options with types and defaults, and CEL rules that compare a document with the one the node runs. The schema lands in the image directory and at /etc/chalkos/schemas on the node; rules compile at build time within a cost limit. chalkctl config apply fetches the running config first, so rules that read oldSelf also run before anything is sent. A node whose image lacks a kind refuses its documents. A fallback boots the old image with the config it understood.

Config kinds ship in the image

The headline idea

A module declares a kind like a CRD: typed fields and CEL rules. The build ships it as JSON Schema, so config is checked against the image that will run it.

With an image staged, config apply checks the set with the staged image's own chalkd check in a sandbox and writes its slot too. --staged on a node without a staged image keeps pending config, unchecked until the next upgrade.     Change the kind in the image's module
    A new required field or API version is fine
  2. 2
    Write config of the new form
    chalkctl validate checks it against the new image
  3. 3

Sources: an image directory chalkctl streams, or an OCI artifact the node pulls by digest, through its Mirror if it has one. chalkctl checks usrhash=, os-release and the config against the image's schemas; the node checks the UKI against db and dbx. The health check: chalkd serves TLS, config applied, no failed units; on cluster nodes the Kubernetes parts. It runs only on counted boots, and nothing rolls a blessed image back by itself. Kubernetes clusters roll control planes one at a time with etcd quorum kept and drain each node; running the command again continues. The config travels only with the secrets file or an admin client file; an operator upgrade carries none. A downgrade is an upgrade to another root hash. No delta updates: about 300 MiB per node for a Kubernetes image.

Upgrades replace the whole image

Config travels with the image

The upgrade carries each node's config; the new image checks it before it is written.

  • The old image keeps its own config for a fallback
  • chalkctl upgrade --rollback on request
  • No deltas: about 300 MiB per node
  • A downgrade is an upgrade to another root hash

Kubernetes layer: the image fixes containerd and the kubelet, the Cluster document names the other images; flannel, kube-proxy and CoreDNS; certificates renew themselves; Registry and Mirror documents for containerd; chalkctl node revoke shuts a node out by name. Router layer: the router validator checks what the documents mean together, and chalkctl links the same code. Without a layer, the node OS takes its network, disks and time servers from config and serves the node API.

The schemas are a build output of their own, system.build.chalkosSchemas, and build in seconds. nix build -L .#nixosConfigurations.<image>.config.system.build.chalkosTestResults shows what each test rendered and refused, with the errors of renderers and checks. The image build fails when a rule does not compile or exceeds its cost limit, when an effect names a unit, output or kind the image lacks, or when the store leaves no room for the next image. chalkos's own end-to-end tests run QEMU VMs under nix flake check: Secure Boot refuses an unsigned image, dm-verity a tampered store, an upgrade that never gets healthy falls back, a three-node HA cluster fails over, two routers peer over BGP.
